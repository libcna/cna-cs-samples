# Primitives3D audit — CSSAMPLE-002

## Result

**The original C# runs unmodified**, and it loads the **official XNA `hudfont.xnb`** through
`Content.Load<SpriteFont>` — which the C++ port could not do, and had to replace with a converted
CNA-native asset. No `../cna-cs` change was needed.

## Content provenance — not this repository's usual source

`rules.md` says to take compiled content byte-for-byte from `../cna-samples/samples/<Port>/Content/`.
**That was not the right source here, and the rule has been amended to say so.**

The C++ port does not ship an `.xnb` for this sample. Its `Content/` holds `hudfont.cnj` and
`hudfont.png`, CNA's own canonical SpriteFont form, generated by `tools/make_font.py`. Its
`missing.md` records why: CNA loaded canonical `.cnj` while XNA's `AlphaBlend` expects a
premultiplied atlas, so the port regenerated the font rather than use the compiled one.

Copying a `.cnj` here would have been the wrong thing twice over: the original C# calls
`Content.Load<SpriteFont>("hudfont")`, which is an `.xnb` contract, and substituting a CNA-native
asset is exactly the kind of runtime substitution `rules.md` forbids.

The source used instead is the **official XNA Content Pipeline output the C++ campaign itself
generated and validated**, retained at:

```text
/rv/tmp/samples/SAMPLE-002-Primitives3DSample_4_0/xna4-original/Primitives3D/bin/x86/Release/Content/hudfont.xnb
sha256 f9ec42ce0d6dd016adc97ca896a37fba0db8a02e790532cb338b8df663b2796d   70 830 bytes
```

It begins `XNBw` — the XNA container magic, `w` for Windows. `../cna-samples`' `SAMPLE-002` audit
records that this file was built from the archived `hudFont.spritefont` by the real pipeline and
then accepted by the real XNA 4.0 runtime under Wine with WineD3D.

**It loads and renders correctly through CNA.NET.** No premultiplication problem appeared, so
whatever forced the C++ port onto `.cnj` either does not affect the `.xnb` reader path or has since
been fixed in CNA. This row does not establish which, and does not need to.

One project-file mistake is worth recording because the next sample can repeat it: `Main` lives in
a separate `static class Program` at the bottom of `Primitives3DGame.cs`, not in the game class.
Pointing `StartupObject` at `Primitives3D.Primitives3DGame` fails with
`CS1558: 'Primitives3DGame' does not have a suitable static 'Main' method`. **Read where `Main`
actually is; do not assume it is in the game class or in a `Program.cs`.**

## Native verification

Debug and Release both build with 0 warnings and 0 errors and run on `OPENGLES3` in an 800x480
window titled `Primitives3D`, exiting 0 on Escape. The frame shows the shaded red cube on
`CornflowerBlue` and the three-line HUD:

```text
A or tap top of screen = Change primitive
B or tap bottom left of screen = Change color
Y or tap bottom right of screen = Toggle wireframe
```

## Comparison with the C++ port

Captured through the same Xvfb/crop route:

| region | result |
|---|---|
| HUD text, `(0,0)`–`(470,90)` | **0 differing pixels of 42 300** |
| whole frame | 55 564 differing pixels, bounding box `(240,97)`–`(545,387)` |

The differing region is exactly the cube and nothing else. The cube rotates, so the two runs were
caught at different rotations — the frame-offset signature `CSSAMPLE-008` established, here confined
by its bounding box to the one animated object.

The HUD result is the interesting one: **the official `.xnb` and the port's converted `.cnj` render
the same text pixel for pixel.** That is independent evidence for both the compiled-font reader
used here and the conversion tool used there.

## Not verified

- **No browser result.** No .NET route to CNA's WEBGL2 backend exists.
- **The other five primitives and the colour and wireframe modes.** The sample cycles cube, sphere,
  cylinder, torus, teapot and a Bezier shape with A/B/Y, and only the default cube was captured.
  Input-driven coverage needs the interaction harness the capture script does not yet have.
- **Gamepad.** Present in the source, no controller attached; Escape was exercised.
